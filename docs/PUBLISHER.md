# TG Proxy Publisher 1.0.4

Отдельная Windows-программа для полуавтоматической публикации уже проверенного
TG Proxy. Windows 1.15.3 и Publisher 1.0.4 находятся в подготовке; фактическая
готовность и результаты указываются в [PROJECT_STATE](PROJECT_STATE.md).

Publisher принимает один immutable bundle и подписанный допуск. Клиентский EXE
для второго канала не пересобирается. Программа не устанавливает Helper и не
меняет адреса обновлений у существующих клиентов. Версия Publisher независима
от Windows-клиента; Android имеет отдельный dev-updater.

Публикация в `byShadow64/tg-proxy` требует проверки текущих веток, всех
workflow, точного source SHA, CI и прав выбранного авторизованного пути.
Документальные download/release-page ссылки запрещены; технические ссылки допустимы.
Другой сервер меняет только назначение ручной загрузки. Закрытые ключи,
токены и профили остаются вне Git и пакета.

## Обычная публикация

1. Запустите `TGProxyPublisher.exe`, откройте вкладку **Пакет** и выберите
   папку `publication`. В ней должны быть `manifest.json`, `source.zip`,
   `RELEASE_NOTES.md` и каталог `assets` с четырьмя публичными файлами:
   `TgWsProxy_windows.exe`, `TgWsProxy_helper.zip`, `SHA256SUMS.txt`, `CHANGELOG.md`.
2. Издатель проверит хеши, версию PE, исходники, соответствие Helper и notes.
   Staging, PRIVATE, prerelease и повреждённые пакеты не допускаются.
   Проверка файлов сама по себе не доказывает, что приложение протестировано.
3. После завершённых тестов отметьте **Сборка протестирована** и нажмите
   **Подтвердить готовность**. Точный набор получит отдельную подпись допуска
   Ed25519. Допуск сохраняется в данных издателя; исходная папка не меняется.
   Ключ подписи используется только на этом ПК, в памяти, после DPAPI-расшифровки.
4. На вкладке **Назначения** проверьте `byShadow64/tg-proxy`, вручную
   введите токен GitHub и выберите сервер. Для передачи workflow токену нужны
   права **Contents: write** и **Actions: write** на выбранный репозиторий.
   Издатель не создаёт токен и не выполняет вход вместо пользователя.
5. Нажмите **Проверить выбранные назначения**, затем на вкладке **Публикация**
   отметьте нужные каналы и нажмите **Опубликовать выбранное**.
6. Для сервера программа подписывает manifest, загружает точные файлы,
   проверяет чтение и заменяет `latest.json` последним атомарным действием.
   После этого проверяет публичное HTTPS-скачивание всех четырёх файлов.
7. Для GitHub программа подготавливает отдельный непубличный входной draft
   с подписанным пакетом и запускает проверенный workflow основной ветки.
   **Передано в GitHub Actions** ещё не означает, что релиз опубликован.
   Нажмите **Проверить результат** или **Открыть GitHub Actions**.

До передачи любого канала программа повторно требует подписанный допуск.
При выборе обоих каналов предварительный конфликт тега, версии или assets
GitHub блокирует запись на сервер. Ошибка авторизации/сети GitHub позволяет
завершить серверный канал; повторный GitHub-запрос сразу не отправляется.

Результаты каналов и локальная история показаны отдельно. Ошибка входа GitHub
не отменяет успешно завершённую публикацию на сервере. Конфликт версии,
тега или байтов не обходится: нужен разбор конфликта или новый номер версии.
Программа не заменяет опубликованные файлы и не передвигает теги.

## Другой сервер

На вкладке **Назначения** нажмите **Другой сервер**. Укажите название,
базовый HTTPS URL, SSH/SFTP-адрес и порт, пользователя, доступный каталог
публикации, способ входа и доверенный SSH-отпечаток.

Кнопка **Получить отпечаток SSH** читает публичный ключ без входа. Сверьте
его с доверенной консолью сервера перед подтверждением. До совпадения pin
реквизиты серверу не отправляются. Ошибка TLS не включает небезопасный режим.
Сервер должен быть заранее настроен для HTTPS и SFTP; форма его не арендует
и не выполняет root-команды. Каталог и ограниченный SFTP-пользователь задаются в административном профиле.

По прямому поручению пользователя **смена назначения меняет только место
загрузки**. Уже установленные клиенты продолжают проверять прежний GitHub и
встроенный адрес HTTPS. Просто загрузить файлы на другой адрес недостаточно,
чтобы клиенты узнали об этом адресе. В этой работе адреса клиентов не меняются.

## Реквизиты и ключи

- Существующий `publisher.dpapi.json` читается без изменения. Если файл
  размещён в известном Codex MSIX cache этого же пользователя, предусмотрен
  ограниченный readonly-поиск; файл можно выбрать вручную.
- Закрытый ключ подписи не включается в пакет, EXE или сервер. DPAPI-файл
  другого пользователя Windows не становится переносимым ключом.
- Сохранение токена/паролей в программе включается отдельным флажком
  **Запомнить реквизиты в Windows (DPAPI)**. Без него реквизиты текущего сеанса
  остаются в памяти. Журнал и краткий отчёт используют безопасные коды.
- Новый сервер использует ту же настроенную подпись, совместимую с клиентом.
  Не подменяйте ключ издателя случайным ключом при смене VPS.

## Отмена, ошибки и повторный запуск

Бюджет SFTP рассчитывается по сумме загрузки и обратного чтения с верхним
пределом 15 минут. Общий тайм-аут и отмена прерывают даже медленный поток
ответов; очистке собственных временных файлов выделяется отдельно до
10 секунд. При потере связи временный lock может сохраниться: чужие
блокировки автоматически не удаляются. Нужна проверка владельца операции
и фактического состояния канала перед повтором.

Сетевые операции выполняются в отдельном потоке. Отмена ожидает безопасного
завершения и очистки; новое действие недоступно до этого момента. Если сервер
уже заменил `latest.json`, отмена не объявляется откатом: результат будет
**Опубликовано; проверка не завершена**.

После сетевого обрыва программа проверяет существующий draft и файлы перед
повторной загрузкой. POST не повторяется вслепую. Неопределённый ответ запуска
workflow требует **Проверить результат**. При 401 или недостаточных правах
нужны ручное исправление реквизитов/прав; повторные попытки не выполняются.
Для rate limits сохраняется пауза GitHub. Токены и IP не сменяются для обхода
ограничений. Это соблюдение протокола API, а не гарантия отсутствия ограничений
или модерации аккаунта.
Статус **Черновик готов; запуск workflow не подтверждён** сохраняет ссылку на
draft и не утверждает, что GitHub не получил запрос. Не повторяйте dispatch
вслепую; сначала проверьте результат и очередь Actions.

## Подготовка пакета из готового EXE

В чистом, закоммиченном стабильном checkout:

```powershell
python packaging/prepare_release.py --exe C:\Build\TgWsProxy.exe `
  --bundle-output C:\Build\release-<version>\publication `
  --build-commit <full-commit-of-the-tested-executable>
```

Эта команда не запускает PyInstaller. Папка результата должна быть новой.
CI может подготовить такой же unsigned-пакет после тестов и frozen smoke;
сам по себе `release_ready` не является допуском к публикации. Выбор пакета
и подпись владельца привязывают фактические bytes к одному выпуску.
Другая сборка уже выпущенной версии требует нового номера, а не перезаписи.

CLI сервера теперь принимает весь пакет, включая его CHANGELOG и notes:

```powershell
python packaging/publish_local_updates.py --bundle C:\Build\release-<version>\publication
```

CLI также проверяет подписанный допуск: предварительно подтвердите тот же
пакет в Publisher. Наличие только `manifest.json` или успешного CI недостаточно.
`--check-connection` проверяет только назначение и не публикует пакет;
старый режим выбора binaries через `--release-dir` не используется.

`--candidate` выбирает ранее настроенный изолированный тестовый каталог.
GUI позволяет явно выбрать отдельный профиль с candidate URL/каталогом.
Staging и PRIVATE нельзя загружать и туда.

## Workflow GitHub

`.github/workflows/build.yml` теперь запускается только вручную на основной
ветке. Вход — ID draft/asset, SHA-256 подписанного архива и stable-тег.
Read-only job проверяет подпись, пакет, коммит, CI и конфликты. Publish job
повторяет проверку и загружает точные файлы с правом `contents: write`.
Пакет остаётся данными: его код и EXE не импортируются и не запускаются.
Публикация не содержит `pip install .`, PyInstaller или `--clobber`.
Зависимости проверяющего инструмента закреплены хешами, Actions — полными SHA.
Последовательная очередь не отменяет уже начавшуюся публикацию.

Перед первым выпуском workflow и инструменты должны находиться в доверенной
основной ветке. Проверьте права, тег и CI **точного source_commit пакета**, а не
только нового HEAD. Сверьте все `.github/workflows` source_commit с default;
при расхождении остановитесь. В новый самостоятельный репозиторий не импортируют
старые private refs или артефакты с другой identity. Bootstrap создаёт отсутствующий
тег только в проверенном ручном Actions-контексте; существующий тег не передвигается.
Недостаток Workflows/Contents/Actions прав блокирует передачу без обхода защиты.
