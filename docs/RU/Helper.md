# Helper: частный и зарегистрированный доступ

Исходники Windows 1.15.3 и Android 0.1.7-dev поддерживают подключение подготовленного
Helper по IP. Если прямое соединение уже работает, Helper не обязателен.
Частный сервер не становится общедоступным после одного ввода IP.

В новом режиме владелец разрешает доступ любому автоматически зарегистрированному
клиенту. Для подключения достаточно IP включённого в registry Helper. Клиент
проверяет доверенный центральный HTTPS, подпись descriptor и pin TLS, получает
lease максимум на 10 минут и обновляет его в памяти. Старый private token не
выдаётся. Ключ P-256 обозначает установку, а не человека, HWID или подлинность APK.
Это bearer lease, без proof-of-possession на data socket.

Для неизвестного IP доступна явная **Настройка по SSH**: подтверждение точного
host key до root-пароля, загрузка проверенного payload и центральная проверка
результата. Старый private Helper переводится только с отдельным, по умолчанию
не отмеченным согласием. Нужны свободные 80/443 и публичный CA IP-сертификат;
сертификат/токен data Helper на 8444 сохраняются. Отмена не доказывает удалённый
откат. Подробные условия: [SSH-настройка](../SSH_SETUP.md),
[модель registry](../DEVICE_REGISTRY.md), [текущее состояние](../PROJECT_STATE.md).
Эти описания не являются подтверждением развёртывания или готовности новой версии.

## Действующая private-схема Windows 1.15.1

# TG WS Helper

Helper перенаправляет WebSocket-подключение через ваш Ubuntu-сервер. Передаваемые данные Telegram остаются зашифрованными MTProto; в новом протоколе дополнительно защищён канал клиент—helper.

## Установка сервера

### Автоматически из программы

1. Откройте **Настройки → Маршруты**, включите **Использовать Helper-server** и раскройте **Настроить VPS по SSH**.
2. Укажите адрес VPS, SSH-порт, пользователя с правами root и пароль. Поддерживаются Ubuntu/Debian с systemd.
3. Нажмите **Установить Helper**, сверьте ключ SSH сервера с данными хостинга и подтвердите подключение.
4. Программа загрузит встроенные исходники, установит зависимости и службу, проверит защищённый порт `8444` и заполнит адрес, порт, fingerprint и токен. Скачивать проект с GitHub на VPS не требуется.
5. Нажмите **Сохранить** и подтвердите перезапуск прокси для применения параметров.

Пароль SSH используется только в памяти во время установки. Существующие сертификат и токен Helper сохраняются при повторной установке. Перед заменой файлов создаётся резервная копия в `/var/backups/tg-helper`; при ошибке запуска восстанавливается предыдущая служба. Установщик добавляет правило для порта Helper, но не включает UFW и не меняет настройки SSH. Если у хостинга есть внешний сетевой экран, порт `8444/tcp` должен быть разрешён и в нём.

### Вручную

На Ubuntu клонируйте этот fork или распакуйте `TgWsProxy_helper.zip` из его релиза. Из корня исходников helper выполните:

```bash
sudo bash deploy_helper.sh
```

Скрипт создаёт TLS-сертификат и случайный токен, ограничивает доступ к ключу и токену системным пользователем службы, устанавливает `tg-helper.service` и открывает защищённый порт `8444/tcp`. В конце появятся IP сервера, SHA-256 fingerprint сертификата и токен. Сохраните их: токен показывается только установщиком и не записывается в логи службы.

## Настройка Windows-клиента

### Подключение к уже установленному Helper по IP

После обновления службы получите одноразовый код в собственной SSH-сессии:

```bash
sudo /opt/tg-helper/venv/bin/python /opt/tg-helper/helper_pairing.py issue
```

Откройте **Настройки → Маршруты**, включите **Использовать Helper-server** и в блоке **Подключить готовый Helper** введите IP сервера и выданный код `TG1.…`. Нажмите **Подключить сервер**, затем **Сохранить**. Для нестандартного порта используйте `IP:порт` или `[IPv6]:порт`. Код не сохраняется в настройках, а поле очищается при запуске, завершении или отмене подключения. Сохранённый токен защищает Windows DPAPI.

Код действует 5 минут и используется один раз; при необходимости владелец может выдать новый. Команда `issue --ttl 600` задаёт срок до 10 минут; одновременно допускается до 32 действующих кодов. Код следует передавать только устройству, которому вы предоставляете доступ: успешное подключение выдаёт существующий токен Helper. Отмена после проверки на сервере может уже израсходовать код.

Сеть передаёт случайный challenge и HMAC, привязанный к фактическому TLS-сертификату; сам код не передаётся. Клиент проверяет HMAC ответа и fingerprint перед использованием токена. Подмена сертификата, неверный, просроченный или повторно использованный код завершают подключение без сохранения. Нет переадресаций или автоматического перехода на открытый протокол. Служба ограничивает число попыток и расходует код атомарно до ответа.

Состояние кодов находится в `/var/lib/tg-helper/pairing.sqlite3`: каталог `0700`, база `0600`, владелец `tg-helper`. В базе хранятся производные ключи, срок и число попыток, без исходных кодов. Systemd создаёт каталог через `StateDirectory=tg-helper`; команда с root сбрасывает права до пользователя службы. У существующего сервера обновите исходники и unit обычным установщиком: он сохраняет сертификат и токен, поэтому уже подключённые устройства продолжают работать. Протокол подключения отключён, если сервер запущен без `--pairing-store`.

### Ручные параметры

Откройте **Настройки → Маршруты** и включите **Использовать Helper-server**. Раскройте **Ручные параметры подключения…**, выберите `tls-pin` и укажите IP сервера, порт `8444`, fingerprint и токен из вывода установки. Здесь же доступна автоматическая настройка **Настроить VPS по SSH**. Сохраните настройки и подтвердите перезапуск прокси. Windows-клиент защищает токен через DPAPI для текущей учётной записи.

Сначала проверяется TLS fingerprint. Только после совпадения клиент передаёт токен и имя маршрута. Ошибка сертификата или авторизации не включает открытый протокол; прокси продолжает работу через обычные upstream-маршруты.

## Переход со старого helper

Старый `~/.tg-proxy/config.json` импортируется в новый конфиг в `%APPDATA%/TgWsProxy/config.json`, а копия сохраняется рядом с исходным файлом как `config.json.pre-upstream.bak`. Если старый helper был включён, его настройки переходят в режим `legacy` на порту `8443`; приложение показывает предупреждение в журнале. Совместимость v1 разрешает прежние `zws2`/`zws4` маршруты, а защищённый v2 принимает только домены текущего upstream-каталога.

Для краткого переходного периода можно запустить установщик сервера с явным флагом:

```bash
sudo bash deploy_helper.sh --allow-legacy
```

После обновления всех клиентов выполните обычную установку без флага `--allow-legacy`. Она заменяет systemd-unit конфигурацией, в которой v1 endpoint выключен. Существующие правила сетевого экрана установщик не удаляет. Для v2 endpoint действуют лимиты: кадр до 16 MiB, handshake до 15 секунд, максимум 256 соединений всего и 32 с одного IP.

Сервис слушает напрямую; конфигурация Nginx и PROXY protocol для helper не используется. Проверка состояния:

```bash
systemctl status tg-helper
journalctl -u tg-helper -f
```

При обновлении установщик переносит старый `/etc/logrotate.d/tg-helper` в `/var/backups/tg-helper/`: прежний hook отправлял SIGHUP и останавливал v1-сервер. Новая служба пишет в journald и продолжает работу при SIGHUP. Подключение к Telegram запрашивает WebSocket-подпротокол `binary`; без него Telegram возвращает HTTP 404.
